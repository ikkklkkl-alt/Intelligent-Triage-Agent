> 按模块整理高频面试问题，每题含参考回答和追问方向，帮助系统性准备。

## 一、AI 应用架构

### Q1：为什么不直接调 DeepSeek API，要做统一 LLM 服务层？

**参考回答**：

直接调 API 在 demo 阶段够用，但在生产系统中会遇到几个实际问题。第一是供应商锁定——如果某天 DeepSeek 涨价或服务不稳定，切换供应商需要改所有调用点的代码。统一服务层做了供应商抽象，切换只需改配置。第二是可观测性——集中管理后，所有 LLM 调用都经过同一个入口，可以统一记录 token 消耗、响应延迟、错误率，这些数据对成本控制和问题排查至关重要。第三是横切关注点——重试策略、超时控制、Token 预算限流，这些逻辑如果散落在各个业务模块中，维护成本很高，而且容易遗漏。统一服务层把这些关注点收敛到一处，业务代码只需要 `await llm.chat(messages)` 一行调用，不需要关心底层细节。

**追问方向**：
- 如果要新增一个 LLM 供应商（比如接入 Claude），你需要改哪些代码？能不能做到只加一个 Provider 类？
- 统一服务层会不会成为性能瓶颈？并发高时怎么处理？
- 你们的 LLM 调用日志具体记录了哪些字段？这些数据怎么用？

### Q2：Token 预算控制怎么做？Redis 不可用时怎么办？

**参考回答**：

Token 预算控制基于 Redis 的原子计数器实现。每天以日期为 key（`imcs:llm_budget:2026-09-04`），每次 LLM 调用前后分别做预估扣减和实际扣减。调用前根据 messages 长度估算输入 token 数，检查当天累计消耗是否接近预算上限；调用后根据实际返回的 usage 信息修正。用 Redis 的 `INCRBY` 保证并发安全。key 设置 24 小时 TTL，自然过期，不需要定时清理。Redis 不可用时的策略是**降级为不限制**，允许请求通过。这是一个有意的取舍：宁可某天超一点预算，也不能因为 Redis 抖动导致整个 LLM 服务不可用。同时会在日志中记录 WARN 级别告警，运维可以事后介入。

**追问方向**：
- 预估 token 数和实际 token 数差距大吗？怎么提高预估精度？
- 如果用户恶意刷接口，光靠 token 预算够吗？还有什么防护手段？
- 有没有考虑过按用户粒度做预算隔离，而不是全局限制？

### Q3：多供应商降级链怎么设计的？为什么选 DeepSeek + Qwen？

**参考回答**：

降级链是一个有序列表，LLM 客户端按顺序尝试每个供应商。主供应商是 DeepSeek，当请求超时（默认 60 秒）、返回 429 限流或 500 错误时，自动切换到备用供应商 Qwen。切换过程对业务代码透明，调用方拿到的响应格式完全一致，只是在日志中会标记 `fallback=true`。如果所有供应商都失败，返回一个预定义的兜底回复（"系统繁忙，请稍后重试"），不会把原始错误暴露给用户。选 DeepSeek 做主供应商是因为它性价比高、中文能力强；选 Qwen 做备用是因为阿里云基础设施稳定、国内延迟低。两者都兼容 OpenAI API 格式，适配器代码量很小，切换成本低。不选 OpenAI 是因为国内网络访问不稳定。

**追问方向**：
- 降级链里的供应商优先级是固定的还是可以根据实时质量动态调整？
- 如果 DeepSeek 返回的内容质量很差但没报错（比如胡言乱语），降级链能检测到吗？
- 两个供应商的模型能力差异大吗？降级后用户体验会有明显变化吗？

## 二、RAG

### Q4：为什么用混合检索而不是纯向量检索？

**参考回答**：

纯向量检索在医疗场景下有两个问题。第一是精确匹配弱——用户问"阿莫西林过敏能吃什么"，Embedding 模型可能把"青霉素"、"头孢"这些语义相近但不完全匹配的药物排在前面，而用户要的是精确的药物名称匹配。全文检索的 BM25 算法天然擅长这种关键词精确匹配。第二是可用性依赖——纯向量检索完全依赖 Embedding 服务，这个服务挂了整个知识库就瘫痪了。混合检索通过向量 + 全文双路检索，再用 RRF 融合排序，兼顾了语义理解和精确匹配。而且当 Embedding 服务不可用时，可以自动降级为纯全文检索，保证系统不会完全不可用。

**追问方向**：
- 混合检索会不会比纯向量检索慢很多？性能开销怎么控制？
- 如果两条路返回的结果差异很大，RRF 融合后会不会互相干扰？
- 检索结果数量太多或太少怎么办？Top-K 怎么选？

### Q5：中文全文检索有什么坑？jieba + simple 配置是怎么解决的？

**参考回答**：

PostgreSQL 内置的全文检索对中文支持不好。默认的文本解析器按空格和标点分词，中文没有天然的词边界，"胸闷气短"会被当作一个整体，无法匹配"胸闷"或"气短"单独出现的文档。社区有 `zhparser` 扩展，但它安装配置复杂、词典更新不及时、在容器环境中部署麻烦。我的方案是用 jieba 做预分词：文档入库时先用 jieba 分词，把"胸闷 气 短"这样的结果存入 tsvector 列，查询时也用 jieba 对用户问题分词再交给 PostgreSQL 匹配。`simple` 配置在这里的作用是不做任何语言特定处理，只保留 jieba 的分词结果，避免 PostgreSQL 的英文词干提取等规则干扰中文。这样做的好处是分词质量完全由 jieba 控制，可以加载医疗专业词典。

**追问方向**：
- jieba 分词的准确率在医疗文本上够用吗？有没有自定义词典？
- 分词结果存入 tsvector 后，原始文档内容和分词结果怎么保持同步？
- 有没有对比过 Elasticsearch 中文分词的效果？

### Q6：RRF 融合的原理是什么？k 参数怎么调？

**参考回答**：

RRF（Reciprocal Rank Fusion）的核心思想是只看排名不看分数。公式是 `score = Σ 1/(k + rank)`，其中 rank 是文档在某个检索器中的排名（从 1 开始），k 是一个常数。这个公式很巧妙——它把不同检索器的分数统一到同一个尺度上，因为余弦相似度和 BM25 分数的量纲完全不同，直接加权没有意义。k 参数控制排名靠后文档的惩罚力度：k 越小，头部文档的权重越高，结果越极端；k 越大，排名差异被平滑，结果越平均。论文推荐的默认值是 60。医疗场景下我选 k=60，因为宁可多给一些候选结果，也不要因为阈值太严漏掉关键信息。实际效果是向量检索的语义匹配和全文检索的精确匹配形成互补。

**追问方向**：
- 有没有做过 k 值的 A/B 测试？不同 k 值对最终分诊准确率的影响大吗？
- RRF 只考虑排名不考虑分数，会不会丢失有用信息？有没有更复杂的融合方案？
- 如果未来加入第三个检索器（比如知识图谱），RRF 的扩展性怎么样？

## 三、Agent 工作流

### Q7：分诊 Agent 的工作流程是怎样的？

**参考回答**：

分诊 Agent 是一个六阶段的状态机。第一阶段是输入审核，检查用户输入是否为空、是否包含心理危机关键词、是否是无关内容。第二阶段是信息提取，从用户描述中识别主诉、症状持续时间、伴随症状等关键信息。第三阶段是 RAG 检索，用提取的关键词去知识库检索相关医学知识。第四阶段是多轮上下文构建，把系统提示、历史对话、RAG 结果拼成完整的 prompt 送给 LLM。第五阶段是流式输出，通过 SSE 把 LLM 的生成实时推给前端。第六阶段是结构化结论，LLM 最终必须输出符合 JSON Schema 的分诊结论，包含推荐科室、紧急程度、可能的诊断和就医建议。如果信息不充分，Agent 会回到第二阶段主动追问用户。如果 RAG 无结果且 LLM 不确定，会触发规则兜底，返回基于关键词-科室映射的通用建议。

**追问方向**：
- 状态机的转移条件是怎么定义的？是 LLM 判断还是规则判断？
- 多轮追问最多能问几轮？有没有防死循环机制？
- 结构化结论的 JSON Schema 是怎么定义的？字段设计有什么考量？

### Q8：为什么用状态机编排而不是 ReAct？

**参考回答**：

ReAct 让 LLM 自主决定下一步行动（思考→行动→观察循环），灵活性很高，但在医疗场景下风险太大。第一是可预测性——ReAct 的行为路径由 LLM 决定，同样的输入可能走完全不同的路径，调试和审计几乎不可能。状态机的状态转移是预定义的，每一步都有日志记录，出了问题可以精确复现。第二是安全性——ReAct 中 LLM 可能"跑偏"，比如跳过输入审核直接给诊断，状态机通过硬编码的转移规则强制执行每一步。第三是成本——ReAct 每一步都需要 LLM 推理来决定下一步，状态机中很多转移是规则驱动的（比如输入审核、JSON 校验），不消耗 Token。第四是延迟——状态机可以跳过不必要的 LLM 调用，比如输入不合法时直接返回提示，不需要经过完整的 RAG + LLM 流程。

**追问方向**：
- 状态机新增一个状态需要改哪些代码？扩展性怎么样？
- 有没有考虑过"状态机 + ReAct 混合"的方案，在某些阶段用 ReAct？
- 如果 LLM 的能力大幅提升，状态机方案会不会显得过于保守？

### Q9：输入审核做了哪些工作？心理危机怎么处理？

**参考回答**：

输入审核是分诊流程的第一道关卡，包含四类检查。内容合法性检查过滤空输入、纯表情、过短文本；心理危机检测通过关键词和正则匹配识别自杀、自伤相关表述；注入攻击防护过滤 prompt injection 尝试；内容相关性检查判断输入是否与医疗相关。心理危机检测是最高优先级，采用硬编码的规则匹配而非 LLM 判断，原因是零延迟——用户表达轻生念头时，系统必须在毫秒级返回危机干预信息（心理援助热线、紧急联系方式），不能有任何 LLM 推理的延迟。检测到危机后，直接返回预设的干预文案，不进入后续分诊流程，同时在日志中记录（脱敏后）供后续分析。这套规则会定期根据实际案例更新关键词库。

**追问方向**：
- 硬编码的关键词匹配误报率高吗？"我不想活了"在什么语境下可能不是真的危机？
- prompt injection 具体防护了哪些攻击模式？
- 如果用户用方言或隐晦表达描述症状，输入审核能识别吗？

## 四、工程化

### Q10：Celery 异步任务为什么用同步 SQLAlchemy？

**参考回答**：

这是一个看似矛盾但实际合理的决定。FastAPI 主应用用 asyncpg（异步驱动）是因为它要处理大量并发的 HTTP 请求，异步可以避免 I/O 阻塞。但 Celery Worker 的场景不同——每个 Worker 是独立进程，任务函数内部是顺序执行的批处理逻辑（比如文档向量化：读文档→分块→调 Embedding API→写数据库），不存在需要同时处理多个请求的压力。用同步驱动有几个好处：代码更简单直接，不需要管理事件循环；调试方便，堆栈清晰；与 Celery 的任务模型天然匹配。要让 Celery 运行异步代码需要引入 `event_loop` 管理或用 `asgiref.sync_to_async`，增加了复杂度但没有实际收益。两套引擎通过不同的连接串配置（`DATABASE_URL` 异步，`DATABASE_URL_SYNC` 同步）共存。

**追问方向**：
- 同步驱动在高并发任务提交时会不会成为瓶颈？
- 两套数据库连接配置怎么管理？连接池参数怎么调？
- 有没有遇到过同步驱动和异步驱动行为不一致的问题？

### Q11：AI 输出不可控怎么保证服务可用？

**参考回答**：

AI 输出不可控是所有 LLM 应用的核心挑战，我从三个层面做防护。第一层是**规则降级**——当 RAG 没有检索到相关知识，或者 LLM 返回的内容不包含有效信息时，系统会回退到基于关键词-科室映射的规则引擎，保证至少能给出一个通用建议。第二层是**内容审核**——LLM 的输出经过后处理，过滤掉可能的幻觉内容（比如确定性的诊断结论），并强制附加免责声明。第三层是**JSON Schema 校验**——要求 LLM 输出结构化 JSON，用 Pydantic 做严格校验；如果 JSON 不合法，尝试用正则从自由文本中提取关键字段；如果还是失败，返回兜底模板。这三层防护确保了即使 LLM 犯错，用户得到的也是"不完美但可用"的服务，而不是报错页面。

**追问方向**：
- Pydantic 校验失败率有多高？什么情况下 LLM 会输出不合法的 JSON？
- "后处理过滤幻觉内容"具体怎么实现？有没有用规则还是也用 LLM？
- 兜底模板的内容是写死的还是根据用户输入动态生成的？

### Q12：这个项目你最不满意的地方是什么？

**参考回答**：

最不满意的是分诊 Agent 的评估体系。目前没有系统性地衡量分诊准确率——我知道规则兜底能覆盖边界情况，LLM 大部分时候表现不错，但缺乏量化的评估数据。如果重新做，我会在上线前构建一个医学 QA 测试集（比如从公开的医疗问答数据集中筛选），对每个版本的分诊结果做自动评估，至少覆盖推荐科室准确率、紧急程度判断正确率、信息遗漏率这几个指标。第二个不满意的地方是 RAG 的检索质量没有闭环反馈——用户没有对分诊结果做"有用/没用"的评价，也就无法用真实反馈来调优检索策略和 Top-K 参数。第三是日志虽然记录了 LLM 调用信息，但没有接入告警系统，Token 消耗突增或降级频繁触发时只能事后发现。

**追问方向**：
- 如果给你两周时间改进，你会优先做哪个？
- 医学 QA 测试集怎么构建？怎么保证标注质量？
- RAG 检索质量的评估指标有哪些？除了准确率还看什么？
